A DNS resolver you can audit.

A forwarding and caching resolver written in cancho: a bounded parser, a fixed arena, and an authority report that shows no foreign code, no processes and no file but its entropy source.

DNS is on every network, and its resolvers have a long history of memory-safety bugs in the code that parses packets. cancho-dns is the same job with no Ffi and no unsafe, and with limits that are checked, not hoped for.

What v1 will doThe plan

Why a resolver, and why cancho

A resolver parses untrusted packets from the network all day, and holds a cache an attacker would like to poison. That makes two properties worth having and worth proving.

The parser cannot be tricked into a crash

Every input is bounded, every refusal has a rule tag, and no input reaches a panic. Name compression pointers, record counts and message sizes all have limits with their own refusals.

No foreign code, no files, no processes

The authority report is derived by the compiler and checked in CI. It cannot yet name the exact upstreams: cancho’s network capability is narrowed once and read by prefix, so v1 keeps the upstream set in a compiled-in table and says so (see the design document).

Memory is sized at start

The cache lives in a fixed arena, as in cancho-cache. Nothing grows without bound, and pauses are bounded by a slice of work.

Built to be read by an agent

Errors are data with stable rule tags and repairs, a check and an explain command say what a configuration or a query would do without sending anything, and the tool describes itself.

What v1 does

A forwarding cache, built and gated: every claim below is measured, with its run recorded in the design document and the numbers file.

In v1

  • DNS over UDP and TCP, with EDNS0 and truncation
  • A cache with TTLs, negative caching and LRU eviction in a fixed arena
  • Forwarding to a fixed set of upstream resolvers, with timeouts, retries and health
  • Local records, overrides and blocklists from a compiled-in file, closed by default
  • Defences that matter: random transaction IDs and ports, 0x20 case randomisation, bailiwick checks, response rate limiting
  • A query log on standard error, off by default, and a latency histogram at histogram.bind
  • An operator surface before it binds: introspect, skill, check, explain, diff, errors as data, a published schema
  • Conformance gates: EDNS compliance from the client side, misbehaving upstreams survived, an RFC coverage table
  • Hardening gates: a 20,000-datagram whole-server fuzz with no trap, every limit at its edge, amplification bounded

Not in v1

  • Iterating from the root servers (a later stage)
  • DNSSEC validation (stage 2: cancho already has RSA, ECDSA and Ed25519)
  • DNS over TLS and HTTPS (TLS needs foreign code today, which would make the authority report unbounded)
  • Zone transfers, dynamic update, views, clustering

How it is built

One thread and one poller, as in the cache. This is the measured row, derived by cancho authority, embedded in the binary at a fixed point, and checked in CI against a ceiling file: what introspect prints is what the compiler derives.

# measured: what the compiler reports, embedded in introspect at a fixed point
args, clock, heap, err_write, io_write, udp_recv, udp_send, conn_accept, conn_read, conn_write, poll,
net_in(""), net_out(""), fs_read("/dev/urandom"), fs_read("conf/")   # no ffi, no fs_write, no exec
# no ffi, no fs_write, no exec; the upstream set is a table in code, not in the type

The open question has an answer, and it is not the one hoped for: measured on cancho, a network capability is narrowed once, its bound is read as host:port one way and as a port the other, and the host is matched by prefix, so a resolver that listens and dials cannot have its upstreams proven by the compiler today. The design ships v1 without that proof and files the language work it needs.

Where it fits

The yardsticks are the resolvers people run. We will measure against them with the cells fixed before the code, and report losses as plainly as wins.

Unbound

  • The reference validating, caching resolver
  • C, mature, DNSSEC and recursion

dnsmasq

  • Small forwarder for routers and labs
  • C, with a record of parser CVEs

CoreDNS

  • Plugin-based, common in Kubernetes
  • Go, a different shape of tool

Knot Resolver

  • Fast, validating, scripted
  • C and Lua

Expectation, stated before measuring — and now measured on ours, on one loopback host: ~146,000 queries/s on the cache-hit path, ~24,000/s over persistent TCP, p50 0.06 ms, a 228 KB binary ready in ~8 ms, memory flat once warm (measured to the end: +0 KiB over four consecutive 150,000-query rounds). The comparison against the resolvers above runs where they are installed — CI installs them — and no ratio is claimed here that was not measured. A big speed win is not the claim; losses will be reported as plainly as wins.

Plan

The design document comes first, and every later task depends on it: scope, the authority row, the cache and security policy, the gates, and the benchmark cells, all fixed before any code. The epic lists the tasks in the order they would be taken: cancho-dns#18.

Status

v1 is built and gated. Every task of the epic has its pull request, every gate is green in CI, and every number lives in the design document with its run. Stage 2 — DNSSEC validation and iterating from the root — is recorded as later work in the epic.
